## หลักการทำงาน
1. อ่าน `CLAUDE.md` ก่อนทุกครั้ง เพื่อรู้ว่ารอบล่าสุดแก้อะไร → ทดสอบสิ่งนั้นก่อน (regression ของงานใหม่)
2. เปิดไฟล์จริงในพรีวิว แล้วตรวจ console error ก่อนเสมอ — error 1 ตัวมักทำทั้งหน้าขาว
3. ทดสอบเป็น flow ของผู้ใช้จริง ไม่ใช่ทีละปุ่ม เช่น สมัคร → สร้างร้าน → เพิ่มสินค้า → ขาย → ดูรายงาน
4. ทดสอบทุกบทบาท (owner / manager / staff / sales / trainer / vendor / worker / customer) และเช็คว่าแท็บ+สิทธิ์ตรงตาม `PERM_PAGES` / `ROLE_TABS`
5. ทดสอบ **ข้อมูลเก่า** ด้วย: ใส่ค่า localStorage รูปแบบเดิม (ไม่มี field ใหม่) → ต้องไม่พัง (บทเรียน `m.parq` / `new Date(at)` = RangeError)
6. ทดสอบสถานะว่าง: ยังไม่มีร้าน / ไม่มีสมาชิก / ไม่มีบิล / ไม่มีคูปอง → ต้องมี empty state ไม่ใช่จอขาว
7. ทดสอบเงินทุกจุดด้วยเลขที่ทำให้พัง: 0 · ติดลบ · ทศนิยม · ยอดเกินคงเหลือ · กดปุ่มซ้ำเร็ว ๆ (double submit)
8. ตรวจกฎธุรกิจที่ห้ามผิด:
   - กระเป๋าเป็น closed-loop → `KDW.withdraw()` ต้อง error เสมอ
   - แพ็กสปอนเซอร์ = ค่าเช่ารายเดือน ไม่มี GP
   - ดีลสปอนเซอร์ในหน้าลูกค้า: ค่าเริ่มต้น = ปิด · ≤2 การ์ด · อยู่หน้า "สั่งสำเร็จ" เท่านั้น · ไม่โชว์หมวดที่ชนกับร้าน
   - taste/impression ต้องอยู่ในเครื่อง ไม่ส่งข้อมูลรายคนออก · ต้องมีปุ่ม "ไม่รับดีล"
9. ตรวจ localStorage key ให้ตรงชื่อจริง (`kd_taste_v1` · `kd_sponsor_impr_v1` · `kd_biz_wallet_v1` · `kd_biz_sales_v1` · `kd_platform_wallet_v1` · `kd_market_vendor_me`) — **ห้ามลบ/ล้าง key ของ user** ให้ทดสอบด้วยการเพิ่มค่าใหม่แล้วคืนค่าเดิม
10. ตรวจมือถือเป็นหลัก (กว้าง 390) — ปุ่มไม่เล็กกว่า 44px · ไม่มี scroll แนวนอน · tabbar ไม่ทับเนื้อหา
11. ห้ามใช้ `window.confirm/alert` เป็นทางผ่าน — ถ้าเจอในโค้ดให้รายงาน (บน PWA/LINE เด้ง dialog เบราว์เซอร์)
12. ถ้าเจอบั๊ก ให้หา**ต้นเหตุ**ในไฟล์ jsx ให้ได้ระดับบรรทัด ก่อนเขียนรายงาน อย่าเดา

## ลำดับความสำคัญของบั๊ก
- P0 หน้าขาว / console error / เงินคำนวณผิด / ข้อมูลหาย
- P1 flow ทำงานต่อไม่ได้ / สิทธิ์รั่ว (เห็นหน้าที่ไม่ควรเห็น) / กดซ้ำได้จนงานซ้ำ
- P2 layout เพี้ยน · empty state หาย · ข้อความ/หน่วยผิด
- P3 ข้อเสนอปรับปรุง (ไม่ใช่บั๊ก)

## รูปแบบรายงาน (ต่อ 1 บั๊ก)
```
[P0] <โมดูล> · <หน้า/ฟังก์ชัน>
ทำอะไร: 1) ... 2) ... 3) ...
ควรได้: ...
ได้จริง: ... (+ ข้อความ error เต็ม)
ต้นเหตุ: <ไฟล์>:<บรรทัด> — <อธิบายสั้น>
เสนอแก้: ... (บอกวิธี ไม่ต้องแก้เอง)
```
ปิดท้ายรายงานด้วย: จำนวนเคสที่ผ่าน/ไม่ผ่าน · สิ่งที่ยังทดสอบไม่ได้และเพราะอะไร

## ข้อความ/โทนที่ใช้
- ไทยสั้น ตรง ไม่ประชด ไม่ชม ไม่สรุปเกินสิ่งที่ทดสอบ
- ห้ามเขียน "เสร็จสมบูรณ์ / ไม่มีบั๊ก" ถ้าไม่ได้ทดสอบครบ — ให้ระบุขอบเขตที่ทดสอบจริง
- ห้ามใส่อีโมจิในรายงาน ยกเว้นหัวข้อสถานะที่ระบบใช้อยู่แล้ว
- ห้ามคัดโค้ดยาว ๆ ลงรายงาน — อ้างไฟล์+บรรทัดพอ

## เทสเสร็จแล้วทำต่อยังไง (ส่งต่อให้แก้โค้ด)
1. เขียนรายงานลง `agents/reports/YYYY-MM-DD-<โมดูล>.md` แล้วสรุปหัวไฟล์เป็นตารางสั้น: `[P?] โมดูล · ไฟล์:บรรทัด · อาการ` เรียง P0 ก่อน
2. ทำ **`agents/fixlist.md`** = คิวงานแก้ 1 ไฟล์รวมทุกโมดูล แต่ละรายการมี: id (`FX-001`) · P · ไฟล์+บรรทัด · สิ่งที่ต้องแก้ (1–3 บรรทัด) · วิธีเทสซ้ำ · สถานะ `todo|fixing|fixed|verified`
3. ส่งเข้าแชทหลักทีเดียวเป็นชุด (ไม่ส่งทีละบั๊ก) โดยบอก 3 อย่าง: แก้ไฟล์ไหน · แก้ตรงไหน · เทสซ้ำยังไง — คนแก้จะไม่ต้องเปิดหาเอง
4. เรียงลำดับแก้: P0 ทั้งหมด → P1 ที่ขวาง flow หลัก → P1 ที่เหลือ → P2 · **P3 ไม่แก้จนกว่า user สั่ง**
5. บั๊กที่ต้นเหตุอยู่ในไฟล์ร่วม (`kd-wallet.jsx` · `kd-sponsor-feed.jsx` · `market-data.jsx` · `platform-api.jsx`) ให้ทำเครื่องหมาย ⚠️shared — แก้แล้วต้องเทสทุกโมดูลที่โหลดไฟล์นั้น ไม่ใช่แค่หน้าที่เจอบั๊ก
6. หลังคนแก้เสร็จ 1 รอบ: เทสซ้ำเฉพาะเคสใน fixlist + เคส flow หลักของโมดูลนั้น → เปลี่ยนสถานะเป็น `verified` หรือเขียนเหตุผลที่ยัง `todo` (ห้ามปิดเองถ้ายังไม่ได้ลองจริง)
7. เมื่อทุก P0/P1 เป็น `verified` แล้วค่อยแจ้งว่าพร้อม deploy — จากนั้น **แชทหลัก**เป็นคนทำ sync `kaidee-deploy/`+`market-deploy/` · bump `?v=`+meta build · bump `sw.js` · zip ส่ง user (เอเจนต์เทสไม่ทำเอง)
8. ปิดรอบด้วยการอัปเดต `CLAUDE.md`: บั๊กที่แก้แล้ว + บั๊กที่ยังค้าง + บทเรียนที่ห้ามพลาดซ้ำ (เช่น guard timestamp ข้อมูลเก่า) เพื่อให้แชทหน้าไม่เทสซ้ำที่เดิม
