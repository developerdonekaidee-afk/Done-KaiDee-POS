ค่าหัวคิวเข้า กระเป๋า/บัญชีของหัวหน้าวินแต่ละวินโดยตรง (แยกตามสีเสื้อ) — แอปไม่เข้ากองกลาง ไม่แบ่งค่าหัวคิวเลย รายได้ของแอปมาจากค่าบริการรายเดือนของร้านทางเดียว

หน้ารับเงิน — หัวหน้าวินตั้งค่าเอง (ไม่ต้องผูกธนาคาร/LINE bank)

หัวหน้าวินแต่ละคนตั้งค่า “หน้ารับเงิน” ของตัวเองในแอป — เลือกได้ 3 โหมด ตามความสะดวก — ตั้งต้น PromptPay ของตัวเอง เมื่อปิดงานระบบสร้าง QR ตามยอดค่าหัวคิวให้แรงงานสแกนโอนตรง — เงินเข้าบัญชีหัวหน้าวินโดยตรง แอปไม่เคยถือเงิน

โหมดรับเงิน (หัวหน้าวินเลือก)ระบบทำอะไร
💵 เงินสด (default ง่ายสุด)แอปโชว์ยอดค่าคิวที่ต้องจ่าย — แรงงานจ่ายสดให้หัวหน้าวินตรง · แอปไม่บันทึก/ไม่ตามยอด — หรือจะกด “รับเงินสดแล้ว” ไว้ดูรายได้ตัวเองก็ได้ (ไม่บังคับ)
💳 PromptPay ตรงโชว์ QR (ค่าเริ่มต้น — ไม่ต้องสมัครธนาคาร/LINE bank) · เปิด/ปิด การแนบสลิปได้
👛 กระเป๋าหักอัตโนมัติออปชันเมื่อโต — แรงงานเติมกระเป๋าล่วงหน้า → หักเข้าวินเรียลไทม์

โหมดเงินสด = ตอบโจทย์หัวหน้าวินที่ “ไม่อยากให้แอปรู้รายได้” — เก็บสดเองได้เลย · แต่ถ้าอยากเห็นรายได้ของตัวเองก็กดบันทึกได้ (สมัครใจ) · ทุกโหมดต้นทุน ฿0 ไม่ติดใบอนุญาตถือเงิน (e-money)

กลไกจับคู่งาน & คิวเรียลไทม์

หมุนเวียนเป็นธรรม — ปฏิเสธหรือไม่ตอบ = ดันท้ายคิว ส่งคิวถัดไปทันที
ร้านเรียกงาน

เลือกชนิดงาน + วินสี + ราคากลาง → ระบบสร้างงานสถานะ open

ดึงคิวที่ 1 ที่ผ่านเงื่อนไข

คิวตำแหน่งน้อยสุดของวินสีนั้น ที่ available และกระเป๋าพอจ่ายค่าหัวคิว

ยิงการ์ดงาน (LINE Flex)

ไทย + พม่า/เขมร · ปุ่ม 🟢 รับ / 🔴 ไม่รับ · จับเวลา 60 วินาที

ปฏิเสธ / ไม่ตอบใน 60 วิ

ดันคนเดิมไปท้ายคิวของวิน → ส่ง offer ให้คิวถัดไป (ข้ามคนเดิม)

รับงาน → ปิดงานด้วย QR

ร้านสแกน QR แรงงานยืนยันจบงาน → หักค่าหัวคิว + ให้รีวิว 1–5⭐ / favorite / blacklist

ถ้าไม่มีแรงงานคนใดในวินสีนั้นว่างหรือกระเป๋าพอ ระบบคืนงานเป็นสถานะ open และแจ้งร้านให้เปลี่ยนสีวินหรือรอสักครู่

โค้ดหัวใจ — เดินคิว & offer หมดเวลา (Node.js / Express)

// หา "คิวถัดไป" = ตำแหน่งน้อยสุดของวินสีนั้น ที่ว่าง + wallet พอ
function nextCandidate(winId, commissionAmt, exclude) {
  return db.prepare(`
    SELECT w.*, q.position FROM queues q
    JOIN workers w ON w.worker_id = q.worker_id
    WHERE q.win_id = ? AND w.status = 'available'
      AND w.wallet_balance >= ? AND w.worker_id NOT IN (${exclude})
    ORDER BY q.position ASC LIMIT 1`).get(winId, commissionAmt);
}

// offer หมดเวลา 60 วิ → ดันคนเดิมท้ายคิว → ส่งคิวถัดไป
function expireOffer(jobId, workerId) {
  const job = getJob(jobId);
  if (job.status !== 'offered' || job.offered_to !== workerId) return;
  pushToBack(workerId, job.win_id);        // หมุนเวียนเป็นธรรม
  advanceQueue(jobId, [workerId]);         // ข้ามคนเดิม
}

โค้ดหัวใจ — ปิดงาน: หัก prepaid → เข้าวิน 100%

// ธุรกรรมเดียว (atomic): หักกระเป๋าแรงงาน → เข้ากระเป๋าวินเต็มจำนวน
const commission = Math.round(job.standard_price * job.commission_rate);

logTxn('worker', worker.id, 'commission_debit', -commission);

โมเดลนี้คือ freemium + แพลตฟอร์มโฆษณา: ค่าฐานต่ำเพื่อดึงคนเข้าให้มากที่สุด (ยิ่งร้าน+แรงงานเยอะ = ข้อมูลและทราฟฟิกเยอะ) แล้วทำเงินจาก (1) แอดออนที่ร้านโตแล้วอยากใช้ (2) สปอนเซอร์ที่อยากเข้าถึงฐานร้าน/แรงงานในตลาด — เก็บทีหลังเมื่อพิสูจน์คุณค่าแล้ว ไม่กันคนเข้าตั้งแต่แรก

แผนสเกล — ตลาดสี่มุมเมือง สู่ 500 ผู้ใช้ในปีนี้

เป้าจริง 500 ร้าน/ผู้ใช้ ภายในปี — สถาปัตยกรรมนี้รองรับสบาย ไม่ต้องรื้อ
สรุป: 500 ผู้ใช้ + งานหลักพัน–หมื่นรายการ/เดือน เป็นปริมาณที่ Cloudflare D1 + Workers รับได้สบายในฟรี/ราคาถูก — คอขวดจริงไม่ใช่ระบบ แต่คือ "ยอดคนสมัคร" กับ "โควตา LINE push" ที่วางแผนไว้แล้ว

ภาระข้อมูลที่ 500 ผู้ใช้

สมมติ 500 ร้าน + 1,000 แรงงาน + 20,000 งาน/เดือน + เดินบัญชี 40,000 แถว/เดือน → ~ครึ่งล้านแถว/ปี = หลัก ร้อย MB เท่านั้น (D1 ฟรีถึง 5GB) · อ่าน/เขียนต่อวินาทีต่ำมากเทียบขีดจำกัด

จุดที่ต้องวางแผนจริง

LINE push (ฟรี 500 ข้อความ/เดือน) จะเป็นตัวแรกที่เต็ม → ขยับเป็นแพ็ก LINE เมื่อโต · dispatch ยิงทีละคน จึงประหยัดข้อความกว่า broadcast · timer 60 วิ เก็บใน DB (offer_expires_at) ไม่พึ่ง memory → รอด worker restart/หลาย instance

ทำอะไรตอนไหน (โตเป็นสเต็ป ไม่ over-build)

0–50 ผู้ใช้ · นำร่อง

D1 + Workers ฟรี · LINE free tier · PromptPay ตรง + ยืนยันเอง · โฟกัสให้ flow จริงลื่น เก็บ feedback

50–200 ผู้ใช้ · เริ่มเก็บเงิน

เปิดค่าฐาน ฿99 (หลังเดือนแรกฟรี) · เพิ่ม index/รายงาน · ขยับแพ็ก LINE push · เริ่มขายแอดออนตัวแรก (ขายของ/จอง)

200–500 ผู้ใช้ · โต

เปิดพื้นที่สปอนเซอร์ · แยก read replica/queue ถ้าจำเป็น (D1 รองรับ) · เพิ่ม prepaid wallet/บอทจับยอดเฉพาะรายที่ต้องการ · ดูเมตริกคิว/เวลาตอบเฉลี่ย

สถาปัตยกรรมไม่ต้องเปลี่ยนตลอดเส้นทางนี้ — D1/Workers scale ตามโหลดอัตโนมัติ · สิ่งที่เพิ่มคือ "ฟีเจอร์/แพ็ก" ไม่ใช่ "รื้อระบบ" · ออกแบบ multi-market ไว้แล้ว (แต่ละตลาดแยก tenant ได้ถ้าขยายออกนอกสี่มุมเมือง)
